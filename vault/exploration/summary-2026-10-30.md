# Grill session summary, 2026-10-30

A summary of the first questioning session on the
[observability architecture exploration](/exploration/observability-architecture.md). The
session was stopped early, at the team's request, with eight questions still open (listed
below). Every point here is the team's account as told in the session. None of it has been
independently verified.

The options drawn from this summary are in
[ADR-001](/decisions/adr-001-observability-architecture.md).

## The problem (draft statement)

When something fails in a shared component, **the team cannot quickly trace the effect
back to its cause**, and **usually finds out from users** rather than from its own systems.

The motivating example is the
[third-party 401 cache poisoning incident](/incidents/third-party-401-cache-poisoning.md).
One call site was missing a newly required API key, and its failure ended up in the shared
cache, which every ECS task reads. The cause was logged once, on one task. The symptoms
appeared everywhere. CPU and latency alerts, Firebase, and checking the app by hand all
missed it. It was caught only because the team was watching after a release.

The problem has three parts:

1. **Correlation, not collection.** Logs are already centralised in CloudWatch Logs.
   What's missing is anything that links an effect to its originating event across tasks,
   services and products ([details](/exploration/log-location.md)).
2. **Detection is manual.** Incidents are usually found through user reports, which the
   team calls "a massive issue". Alerts watch infrastructure strain, not whether the
   service is working correctly ([detection](/exploration/detection.md),
   [audience and use](/exploration/audience-and-use.md)).
3. **Silos.** The app and website teams share infrastructure but watch only their own
   products. In the incident, both investigated at once, separately. The shared components
   are jointly owned and in practice unowned, and the web team knows the infrastructure
   best ([team silos](/exploration/team-silos.md),
   [shared platform](/exploration/shared-platform.md)).

## Current estate

- Request path: **WAF, then CloudFront** (which also routes by path), **then a load
  balancer, then ECS** ([current estate](/exploration/current-estate.md)).
- **One ECS service for the app and several for the website**, split by request path, all
  running **the same Docker image** ([service topology](/exploration/service-topology.md)).
- A shared **ElastiCache cache running Valkey**. Nothing records what is written to it or
  by whom ([shared cache provenance](/exploration/cache-provenance.md)).
- Tooling: **CloudWatch Logs**, plus **Slack alerts on CPU and load balancer latency**,
  plus **Firebase** on the app side. Nothing else is known: no dashboards, application
  metrics, tracing or combined view ([existing tooling](/exploration/existing-tooling.md),
  [Firebase and client-side signals](/exploration/client-side-signals.md)).

## Constraints

- **AWS must be the platform** (a hard rule).
- **Outside tools are allowed but need procurement.**
- **Cost must be considered** for every option.

See [constraints](/exploration/constraints.md).

## What the team wants from the exploration

- A **pinned-down problem statement** (drafted above).
- **Several options**, each with a **sketched target architecture**.
- A **comparison**: pros, cons, and the heuristics for when each option fits.
- Options that **mitigate** as well as options that **solve**.
- **Reasoning shown throughout**, so the team can learn from it.
- On alerting: **a mix of symptom-based and cause-based alerts**, with the reasoning for
  each explained. The aim is to know **before a callout**, definitely **before users get a
  poor experience**, and before the website looks bad.

See [shape of a good outcome](/exploration/good-outcome.md) and
[alert design](/exploration/alert-design.md).

## Assumptions register

Surfaced during questioning. Unconfirmed items are marked.

- Centralised log search already exists, so options build on CloudWatch Logs rather than
  replacing it.
- Infrastructure alerts (CPU, latency) don't cover correctness failures. A cached error is
  fast and cheap to serve.
- Options need a **shared view across both products** and support for cross-team incident
  work, not only better tools inside each team's view.
- Because every service runs the same image, telemetry must carry the **service and
  product** that emitted it.
- An option that only one team can run or interpret would deepen the silo.
- Knowing before users do means relying on **leading indicators** (cause-based signals).
  Symptom alerts fire only once users are already affected.
- *Unconfirmed:* the refresh path caches whatever comes back, including errors.
- *Unconfirmed:* the Slack alerts are CloudWatch alarms on default metrics.
- *Unconfirmed:* "AWS must be the platform" means observability builds on AWS by default,
  with outside tools as procured exceptions.
- *Unconfirmed:* the primary audience for the output is the team itself, not procurement
  or leadership.
