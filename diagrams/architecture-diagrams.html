1. Current estate

Today, as described in the grill session

One Docker image, run as one app service and several website services split by request path. All of them share a Valkey cache and call the third party. Observability is CloudWatch Logs, plus Slack alerts on CPU and load balancer latency, plus Firebase for the app.

2. How the incident spread

Context: why the options matter

One refresh call missing the API key put an error into the shared cache. Every task then served it. The cause was logged once, on one task, and no alert fired.

sequenceDiagram
  participant T1 as App task doing refresh
  participant TP as Third party
  participant C as Valkey cache
  participant TN as All other tasks
  participant U as Users
  participant L as CloudWatch Logs
  T1->>TP: Refresh call without API key
  TP-->>T1: 401 Unauthorized
  T1->>L: One error line, on this task only
  T1->>C: Writes error state
  U->>TN: Requests
  TN->>C: Read
  C-->>TN: Cached error
  TN-->>U: Error or bad data
  Note over C,L: No alert fires. CPU and latency look normal

4. Option B: OpenTelemetry into AWS-native backends

Solve · no procurement · medium cost

OpenTelemetry instrumentation with an ADOT collector sidecar, exporting to X-Ray, CloudWatch and Application Signals (service map, dependencies, SLOs). Includes cache provenance, an app change.

5. Option C: OpenTelemetry into an external product

Solve · procurement required · medium to high cost

The same instrumentation as B, but exported to an outside product such as Honeycomb, Datadog or Grafana Cloud. The best investigation experience, but telemetry leaves AWS.

6. Option D: OpenTelemetry into AWS-managed open source

Solve · billed through AWS (procurement unconfirmed) · medium cost · highest ownership load

The same instrumentation, exported to Amazon Managed Service for Prometheus, X-Ray or OpenSearch, and CloudWatch Logs, all viewed in Amazon Managed Grafana.

7. Cache provenance (applies to B, C and D)

An app change: the piece that links a bad read to the write that caused it

Tracing follows a single request, but the bad entry was written by one call and read later by others. Storing the writer's trace ID with each value links the two, and refusing to cache failures stops the poisoning altogether.

sequenceDiagram
  participant W as Writer task
  participant TP as Third party
  participant C as Valkey cache
  participant R as Reader task
  participant O as Tracing backend
  W->>TP: Refresh call, span with trace id W1
  TP-->>W: Response
  alt Response is not a success
    W->>O: Span marked as error, caller and status recorded
    W--xC: Not cached, previous value kept
  else Response is a success
    W->>C: Store value plus writer trace id W1, service and time
  end
  R->>C: Read
  C-->>R: Value plus provenance
  R->>O: Span links to W1
  Note over R,O: From any bad read, go straight to the write that caused it

8. Alert routing: symptom-based and cause-based

Applies to every option

Symptom alerts tell you users are affected and go to people. Cause signals point at the culprit: the strongest early warnings alert, and the rest feed a shared dashboard for investigation.

flowchart TB
  subgraph SYM["Symptom-based: users are affected"]
    S1["User-facing error rate"]
    S2["Synthetic check failing"]
    S3["SLO burn rate"]
  end
  subgraph CAU["Cause-based: a component is failing"]
    C1["Dependency 4xx and 5xx by caller"]
    C2["Non-success responses being cached"]
    C3["Cache refresh failures"]
  end
  S1 & S2 & S3 -->|page or Slack| ACT["Act now"]
  C1 & C2 -->|strong early warnings| EW["Slack early warning"]
  C1 & C2 & C3 --> DASH["Shared dashboard
for investigation"]
